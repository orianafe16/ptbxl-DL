### B1 — Likelihood rule for the superclass labels stated without checking
- Date, chat, detected by: 2026-11-20, DL 01 Data; detected by the assistant itself when OF and MM asked it to analyse the best option; logged at their request.
- Prompt: OF and MM asked which decisions were needed before writing the label code ("¿Qué es lo mejor?").
- Wrong answer: the assistant proposed to assign a superclass only when the SCP code has likelihood > 0, claiming that "this is what the reference benchmark does" (stated from memory, without a source).
- Evidence that it was wrong: `example_physionet.py`, shipped with PTB-XL 1.0.3, assigns the superclass for every diagnostic code regardless of its likelihood. With that rule the counts are NORM 9514, MI 5469, STTC 5235, CD 4898, HYP 2649, equal to the table of the PhysioNet page; with likelihood > 0, STTC drops to 5108 (127 records lost) and the class-count test would fail.
- Correction: likelihood ignored (DECISIONS D2, entry of 2026-11-20).
- Reproduction (how to check it again): `python -m src.prepare_data` prints the counts with the adopted rule (run by MM on 2026-11-20: equal to the PhysioNet table). For the wrong rule, change `for code in codes` in `src/data.py::superclass_labels` to skip codes whose value in `scp_codes` is 0 and compare STTC.

### B4 — `report --fast` stopped when the trivial run was listed
- Date, chat, detected by: 2026-11-20, DL 04 Dense; detected by the assistant itself when it found no `dense_summary_fast.json` among the outputs of OF's smoke test, and reproduced on a synthetic cache.
- Prompt: OF and MM asked for the complete Dense block; the assistant wrote `src/dense_experiments.py`, whose `all --fast` step should test the whole pipeline.
- Wrong answer: in `--fast` mode, `build_summary` paired the final runs with the trivial model on the test fold. The `--fast` runs only see 256 random test records, the trivial run the whole fold, so `paired_diff` stopped with "differ in test_ecg_id". The assistant's own tests did not catch it because their temporary `runs.json` had no trivial run.
- Evidence that it was wrong: the smoke test left no `_fast` summary, tables or figures; the same call on a synthetic cache with a full-fold trivial run raises `ValueError: ... differ in test_ecg_id`.
- Correction: no trivial comparison with `--fast` (the full runs, which use the same test records, were not affected); the test fixture now lists a full-fold trivial run, plus a regression test.
- Reproduction (how to check it again): in `src/dense_experiments.py::build_summary` remove `and not fast` from the trivial-comparison condition and run `python -m pytest -q tests/test_dense.py`: `test_fast_summary_skips_the_trivial_comparison` fails.

### B5 — Wrong cause given for `git_dirty: true` in the trivial run
- Date, chat, detected by: 2026-11-20, DL 04 Dense; detected by the assistant from the `git status --short` pasted by OF.
- Prompt: in chat DL 03 the assistant explained why the log of `trivial_e2e_s42_20261120-183809` says `git_dirty: true`.
- Wrong answer: "the run was made before the code was committed" (`docs/blocks/03_eval_train.md`, HANDOFF entry of chat 03), stated as the cause.
- Evidence that it was wrong: every Dense run, all made after commit `fcc3c3b` with code identical to it, also says `git_dirty: true`. `run_experiment` writes the run's own predictions file before `runlog.environment()` runs `git status --porcelain`, which lists untracked files, so any full run is "dirty".
- Correction: cause written in `docs/blocks/04_dense.md` and HANDOFF; fix proposed for chat 00/03 (`--untracked-files=no`), not applied in chat 04 because `src/runlog.py` is shared code.
- Reproduction (how to check it again): with a clean working tree, run `python -m src.train --model trivial --max-epochs 1 --tag check` and read `meta.git_dirty` in its log: `true`.

### B6 — Code comment said the positional-encoding buffer is saved in the checkpoint
- Date, chat, detected by: 2026-11-21, DL 07 Self-attention and Transformer; detected by the assistant itself while checking the PyTorch details of the block note against the code, after the runs.
- Prompt: OF and MM asked for the complete Transformer block; the assistant wrote `src/models/transformer.py` (committed in f11e501).
- Wrong answer: the comment above `self.register_buffer("pe", ..., persistent=False)` said "A buffer: saved with the model and moved to the GPU with it".
- Evidence that it was wrong: with `persistent=False` PyTorch leaves the buffer out of `state_dict()`, so it is not in the checkpoint: `'pe' in TransformerClassifier().state_dict()` is `False` while `hasattr(model, 'pe')` is `True`.
- Correction: comment rewritten ("moved to the GPU with the model ... persistent=False keeps it out of the state_dict (checkpoint); it is rebuilt here"). Code behaviour unchanged, so the runs and results stand; loading the checkpoints works because the table is rebuilt when the model is created.
- Reproduction (how to check it again): `python -c "from src.models.transformer import TransformerClassifier as T; print('pe' in T().state_dict())"` prints `False`.

\subsection{How the assistant was kept under control}

An assistant that writes whole pipelines makes it easy to accept results one cannot explain. The rules we
followed:
\begin{enumerate}[leftmargin=1.4em,itemsep=1pt]
  \item \textbf{Decisions before code.} Each block began with a written proposal (architecture, ablation
        grid, seeds, selection rule, outputs). We accepted or changed it, it was written as a dated entry of
        \texttt{docs/DECISIONS.md}, and only then was code written. A decision changes only with a new
        dated entry.
  \item \textbf{We execute, the assistant does not.} The assistant never trained on the real data. We ran
        the tests, the smoke runs (\texttt{--fast}) and the real runs, and pasted the output back. No result
        counts until one of us has run it; the runs of my blocks were executed by me.
  \item \textbf{No number typed by hand.} Every number of the reports is a macro generated from the run logs
        (Section~\ref{sec:code}).
  \item \textbf{No claim without a checked quote.} Literature claims come only from quotes checked against
        the PDFs; interpretations that no number supports are written as hypotheses.
  \item \textbf{Every figure inspected} against the numbers it shows before it was accepted.
  \item \textbf{Every write checked.} After older copies of files reached the folder several times, every
        file written by the assistant is compared with the intended version before it is reported as written.
  \item \textbf{One block per conversation.} The work was split into one conversation per block, which share
        only the project folder; each closes with a block note, the updated plan and log, and our commit.
\end{enumerate}
For my blocks I went through every function with the assistant's explanation before running it, because
the oral defence asks about the theory and about specific lines of the code.
